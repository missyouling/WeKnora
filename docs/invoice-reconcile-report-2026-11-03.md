# 发票「多页明细串页 + 税率错标」修复报告（2026-11-03）

## 一、根因

### 1. 明细串页（P1/P2 显示 P12/P14 的明细）

`OverlayDeterministicInvoiceFields` 把全文正则抓到的明细行**按数组下标**回填：

```go
rows := flatItemRowRe.FindAllStringSubmatch(full, -1)
for i := range res.Invoices {
    if i < len(rows) { applyFlatItemRow(&res.Invoices[i], rows[i]) }  // ← 错在这里
}
```

真机文件 `通行费电子票据汇总单(发票).pdf`（19 页 19 票）里，只有第 12、14 页的
明细是「整行压进一个 colspan 单元格」的形态，能被扁平正则命中；其余 17 页是
「一格一列」的 HTML 表格，正则打不中。于是：

| 数组下标 | 发票 | 票面金额 | 错误拿到的明细行 |
|---|---|---|---|
| 0 | P1 `26507906731100002846` | 68.82 | P12 的 2.62 / 3% / 0.08 |
| 1 | P2 `26507903331100005079` | 198.09 | P14 的 6.45 / 3% / 0.19 |

### 2. 税率错标（198.09 被标 3%）

同一处回填把 P14 的 `3%` 写进了 P2 的明细行。发票级税率本是 9%，但列表筛选用
「票级税率 **或任一明细税率** 命中」判定，所以筛 3% 会命中这张 9% 的票，合计行
`合计金额 × 3%` 与 `合计税额` 自然对不上（差 198.09 × 6% = 11.89 元）。

## 二、修复

### 后端

| 改动 | 文件 |
|---|---|
| 明细行按**物理页码**配对（一页一票才配对；否则退回「行数 == 发票数」严格 1:1） | `knowledge_invoice_extract.go` |
| 新增 `ReconcileInvoiceFinancials`：标准档位（0/1/3/5/6/9/13）反推 + 价税合计恒等式 | `invoice_financial_reconcile.go`（新） |
| 按每张票自己那一页的原文重建明细（页内唯一数据行才重建） | 同上 |
| HTML 规则：合并格取到车牌后不再 `continue`，补回「通行日期起」 | `knowledge_invoice_html_rules.go` |
| 落库前 / 手动保存时执行四元校验 + 明细日期归一 | `knowledge_business.go` |
| 启动幂等修复：存量按页重建 + 备注同步（只对可疑文件加载 chunks） | `invoice_items_repair.go`（新） |

纠偏规则（只认数学证据，不猜）：

- `|金额 × 标准档 − 税额| ≤ 0.02` 且当前税率误差 `> 0.05` → 改税率（票级 + 明细）；
- 税额为 0 时**不反推**（免税 / 税额未提取不可区分），避免把 9% 静默改成 0%；
- 一票多档（13% 设备 + 9% 电信 + 6% 增值）不按票级税率判错；
- `金额 + 税额 ≠ 价税合计` 且无法用标准档闭环 → 只出告警，交给人工。

### 前端

- 详情抽屉定位子记录：票号优先、页码次之，**取消 `parsed[0]` 兜底**；
- 明细严格取该子记录自身的 `items`，绝不回退文档顶层 `custom_metadata.items`。
