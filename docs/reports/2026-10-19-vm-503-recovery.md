## 三、根因

### 3.1 后端：`container.go` 从未设置 `MaxOpenConns`

```go
// 修复前
if os.Getenv("DB_DRIVER") == "sqlite" {
    sqlDB.SetMaxOpenConns(1)
} else {
    sqlDB.SetMaxIdleConns(10)   // ← 只设了闲置数
}
sqlDB.SetConnMaxLifetime(10 * time.Minute)
```

- `database/sql` 的 `MaxOpenConns` 默认值是 **0 = 无限**。
- 后端常态占住 **10 条闲置连接**（实测 `ss -tn | grep :5432` = 10）。
- 上游 Supabase session 模式 pooler 上限 **15**，只剩 5 条给突发。
- 提取高峰时每张图都要写 `resource_bindings` 与 `knowledge_processing_spans`，
  并发申请第 11~15+ 条连接 → 直接打穿 → 连鉴权用的 token 查询都拿不到连接。

### 3.2 为什么表现成前端 503

上一轮为防"连接故障被误报成 401 从而踢登录"，把鉴权存储故障映射成了
`503 auth_backend_unavailable`。于是池一打满，两个业务接口同时 503，页面整块报错。

### 3.3 前端：轮询放大故障（非起因）

`useBusinessPolling.ts` 原来只有 `scanOnce` 有 `busy` 护栏：

```ts
const scanOnce = async () => { if (busy) return; busy = true; ... }
const tick = async () => { await scanOnce(); if (onTick) await onTick() }  // ← 无锁
timer = setInterval(async () => { await tick() }, 3000)                   // ← 固定间隔
```

- `onTick`（发票页 `loadFiles`）没有在途锁：列表接口一旦慢于 3s，
  每一轮都会再起一个 `onTick`，请求层层叠加。
- 失败被 `catch {}` 完全吞掉，既不上报也不降频 → 后端越慢，压力越大。

## 四、修复

### 4.1 连接池必须有上限（根因修复）

`internal/container/container.go`：

```go
func dbPoolSettings(getenv func(string) string) (maxOpen, maxIdle int) {
    const (defMaxOpen = 8; defMaxIdle = 4)
    parse := func(key string, def int) int {
        raw := strings.TrimSpace(getenv(key))
        if raw == "" { return def }
        n, err := strconv.Atoi(raw)
        if err != nil || n <= 0 { return def }  // 永不返回 0（无限）
        return n
    }
    maxOpen = parse("DB_MAX_OPEN_CONNS", defMaxOpen)
    maxIdle = parse("DB_MAX_IDLE_CONNS", defMaxIdle)
    if maxIdle > maxOpen { maxIdle = maxOpen }
    return
}
```

并在 `initDatabase` 中应用：

```go
maxOpen, maxIdle := dbPoolSettings(os.Getenv)
sqlDB.SetMaxOpenConns(maxOpen)
sqlDB.SetMaxIdleConns(maxIdle)
sqlDB.SetConnMaxIdleTime(2 * time.Minute)   // 及时归还上游槽位
logger.Infof(ctx, "DB pool configured: max_open=%d max_idle=%d", maxOpen, maxIdle)
```

效果：超出并发的请求在**本地排队**，上游永远拿不到第 16 条连接。

VM `.env` 显式落参：`DB_MAX_OPEN_CONNS=8`、`DB_MAX_IDLE_CONNS=4`。

### 4.2 前端轮询加固

- **整轮在途锁 `tickBusy`**：同一时间只有一轮（扫描 + 刷新）在飞，重入直接跳过。
- **指数退避**：`pollingBackoffDelay(base, failures) = base * 2^n`，封顶 60s；
  连续失败计数内聚在 `tick` 内，任一轮成功即归零。
- **`setInterval` → `setTimeout` 链式调度**：只有链式才能按可变退避间隔排下一轮。
  `stop()` 置 `running=false`，在飞的一轮结束后不再续排。

## 八、遗留与建议

1. **本次只治"打穿上游"这一层。** 8 条连接若成为瓶颈，优先把 DB 切到
   transaction pooler（`:6543`，代码已支持 `WEKNORA_DB_SIMPLE_PROTOCOL=true`），
   而不是简单调大 `DB_MAX_OPEN_CONNS`——后者会重新打穿 15 条上限。
2. **生产环境独立配参**：若为直连（非 pooler），`DB_MAX_OPEN_CONNS` 可上调到 20+。
3. **建议给 `resource_bindings` / `knowledge_processing_spans` 加批量写入**：
   当前每张图 1 条 INSERT（日志里 SLOW SQL 稳定 360ms），是连接消耗的主要来源。
