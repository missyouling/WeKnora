## 1. 重复造轮子与组件/逻辑冗余

### 1.1 两套 PDF 排版引擎并存（影响最大）

| 引擎 | 位置 | 使用方 | 职责 |
|---|---|---|---|
| `generateCatalogPdf` | `useCatalogPdf.ts:101` | 9 个页面 | 「打印目录」——横向多列清单 |
| `generateStatementPdf` | `useCatalogPdf.ts:413` | 3 个页面 | 「打印清单」——带概览卡片/指标/KPI 的账单 |

- **同一文件内两套排版逻辑**（页眉/分页/表格绘制各写一遍），只共享 `loadCatalogFont`。
- `SolarManagement` / `TenantBilling` / `UtilitiesManagement` 三个页面**同时**调用两者（目录 vs 清单）。
- `UtilityMeterTab` 只用 catalog，没有清单能力。

**结论**：不是「必须两套」，而是「目录是清单的简化形态」。可合并为单一引擎 + `layout` 参数（`catalog` / `statement`），预计减少 200~250 行重复绘制代码。

**风险**：中。9 个页面的目录打印都要回归（含非能耗的发票/合同/制度/奖惩/车队）。

### 1.2 费用清单的 PDF 构造器内联在页面里

`buildStatementDoc` / `statementKpis` / `statementMeta` / `feeTableOf`（合计约 400 行）写在 `TenantBilling.vue` 内，而**市电/光伏的同类构造器已抽出**到 `energyBillStatements.ts`（`buildUtilityBillStatementDoc` / `buildSolarBillStatementDoc`）。

**结论**：同类逻辑三种归属（两个在 ts、一个在 vue），违反「同类同层」。建议把费用清单构造器迁到 `energyBillStatements.ts`，`TenantBilling.vue` 只保留数据准备。

**风险**：低（纯搬迁 + 单测已有 `billingPrintStatement.test.ts` 兜底）。

### 1.3 数字/金额格式化函数散落 7 处

| 文件 | 自定义的格式化/取整函数 |
|---|---|
| `TenantBilling.vue` | `money2` `num2` `rateText` `round2Num` `fmtMoney` `fmtKwh` |
| `UtilitiesManagement.vue` | `fmtMoney` `fmtKwh` `round2` |
| `SolarManagement.vue` | `fmtMoney` `fmtKwh` |
| `UtilityMeterTab.vue` | `fmtMoney` `fmtNum` |
| `MeterRecordDrawer.vue` / `MeterSettingsPanel.vue` / `FleetRecordList.vue` | 各自一份 |

**实际后果**（已发生过）：
- `round2` 是否带 `1e-6` 补偿，直接决定「788.0849999 → 788.08 还是 788.09」；第 20 轮前端与 Go 各补一次。
- `money2` 与 `fmtMoney` 对 0 的处理不同（`0.00` vs `—`），同一列在不同页面表现不一致。

**结论**：抽 `formatNumber.ts`（`round2` / `money2` / `num2` / `pct` / `rateText`），全模块单一实现。

**风险**：低，但**改动面广**（7 个文件、约 40 处调用），需逐页目视核对。

### 1.4 孤立页面 `EnergyManagement.vue`

- 路由 `/platform/daily-affairs/energy` 可达（`router` 第 261 行）。
- **全站没有任何入口链接到它**（侧边栏、KPI 卡片、跳转均无）。
- 功能与 `UtilitiesManagement` 的「电费核算 / 水费核算 / 气费核算」KPI 卡高度重叠（都是账期台账 + 读数反算）。

**结论**：要么给它一个入口并明确边界，要么下线（保留路由重定向到 `/utilities`）。**需要产品确认**，我不擅自删。

**风险**：低（确认后一次改动）。

### 1.5 字段配置的「一份数据、两套 UI」

- `FleetCertPanel`（设置 → 字段定义 → 持睿汽车分组）与 `TenantSettingsPanel`（设置 → 清单设置 → 分摊子项）**读写同一份 `subs` 与 `billing_tenant_items`**。
- 第 19 轮加的双向同步（`tenantGroupSync.ts`）本质是**补丁**：两个 UI 各自可以改宽度/启用，靠保存时互相回写保持收敛。

**结论**：长期应收敛为「一个写入口 + 一个只读视图」。短期可保留，但需补一条「两端不一致时以哪端为准」的显式规则（当前是「最后一次保存者胜」）。

**风险**：中（涉及用户操作习惯，需产品定）。

### 1.6 明细展开子表的三种实现

| 场景 | 实现 | 位置 |
|---|---|---|
| 费用清单大类展开（市场化购电费 +/−） | `fee-group-panel` | `TenantBilling.vue` |
| 核算分时表四时段 | `sub-row` | `UtilityMeterTab.vue` |
| 字段配置子项（明细子项 / 大类成员） | `sub-inline` / `child-drawer` | `FleetCertPanel.vue` |

三者数据结构不同（列×行 / 时段 / 字段元数据），**不建议强行统一**；但样式（行高、缩进、hover、分割线）应抽到共享 CSS，当前各写一份。

**风险**：低。

第 19 轮真机暴露的「持睿分组混入 16 个业主视角列」正是这类缺口 —— 单测全绿但六端已经不一致。

**建议**：加一条纯函数级「六端字段集合 diff」单测：给定 subs + items，断言
`buildColumnsFromSubs` / `buildDetailFieldDefs` / `buildStatementDoc().tables[].columns` / `buildRowTips` 四处的 key 集合相等。
**这属于 P0，因为它防的是「数据正确但展示错位」这类最难查的问题。**

### 2.3 前后端职责边界 —— 基本清晰，但有一处越界

- 分摊/分时/取值口径在**前端** `tenantBillingSources.ts` 与**后端** `billing.go` **各实现一遍**（必须双份，因为列表要实时算、账单要落库）。
- 两份实现靠人工保持同步，第 20 轮我改了 5 处口径，前后端各改一遍 —— **没有任何机制保证两边一致**。

**建议（P1）**：把「Excel 基准值」做成一份共享 fixture（JSON），前端单测与 Go 单测都读它做断言。这样口径漂移会在 CI 直接红。

### 2.5 异常与日志规范 —— 合规度较高

- 后端：`c.Error(errors.NewXxxError(...))` 统一，无 `c.JSON(400, ...)` 硬编码 ✓；`logger.*` 统一，无 `fmt.Print` ✓。
- **问题**：`internal/handler/billing.go` 有 **12 处** `_ = xxx.Error` / `_ = err` 静默忽略。多数是「统计类查询失败不影响主流程」，但未区分「可忽略」与「应告警」，排障时无迹可循。
- 前端：`catch { /* ignore */ }` 在 `localStorage` 读写处（可接受），但 `syncItemsToCostList` / `syncFieldsToTenantItems` 的失败只 `console.warn`，用户在界面上完全无感 —— 双向同步失败时数据会静默分叉。

**建议（P1）**：同步失败改为 `MessagePlugin.warning` + 上报（至少让用户知道「字段定义未同步」）。

## 3. 数据库与数据层隐患

### 3.1 `billing_records.ratio` 精度不足 —— 已确认

- 列定义：`numeric(18,6)`。
- 实际需要 8 位（`0.21235625`），落库被截断为 `0.212356`。
- 后端计算用内存值（正确），前端第 20 轮已改为**现算**绕过（`ratioOfMonth` 用 `starTotal / billKwh`）。
- **但**：任何新代码读 `rec.ratio` 做乘法仍会差 1 分（`44,000 × 0.212356 = 9,343.66` vs 标准 `9,343.67`）。

**建议（P0）**：`ALTER TABLE billing_records ALTER COLUMN ratio TYPE numeric(18,10)`。
**风险**：低（只加宽精度，不改变值域）；但需在低峰期执行并确认 ORM 无 `precision` 硬编码。

### 3.2 `billing_records.total_fee` 语义模糊

- 该字段是「工业电费 + 宿舍电费 + **水费**」（第 20 轮实测：`101414.04 + 930 + 939.60 = 103283.64`）。
- 而列表上的「电费合计」列 = 工业 + 宿舍 = `102344.04`。
- 两个「合计」差一份水费，命名上完全看不出来。

**建议（P1）**：重命名为 `grand_total`（含水电）或拆成 `elec_total` / `water_total` 两列；至少加注释与字段说明。

### 3.3 重复上传账单 —— **上一轮的判断需要更正**

实测：`2026-09` 确实有两条 `2026.09月电费账单.pdf`，但其中 `23773e75` 的 `deleted_at IS NOT NULL`（已软删）。
`loadUtilityBillByMonth` 已带 `deleted_at IS NULL` 条件，**只会取到 `1db0ab9e`**。

**结论：不存在「同月多条有效账单」问题。** 上一轮我按未过滤 `deleted_at` 的查询误判，此处更正。
遗留的是 `1db0ab9e` 的 `meter_readings` 曾被历史版本写成缩水值（第 20 轮已修，备份表 `_bk_knowledge_meta_20261102`）。

**建议（P2）**：加一条启动期健康检查，扫描「账单 meter_readings 的 `line_loss` 明显偏离账单 `bill_kwh` 比例」的记录并告警，防止历史脏数据再次被当成真值。

### 3.4 `fleet_categories.subs` 是裸 JSON，无 schema 约束

- 字段定义全部存在一个 `jsonb` 数组里（`name/label/enabled/is_default/data_type/width/group/group_label/source/sub_fields`）。
- 拼写错误（如 `isDefault` vs `is_default`）、多余键、跨分组污染**数据库层完全拦不住** —— 第 19 轮的 16 列污染就是这么进去的。
- 目前靠后端 `SanitizeTenantGroupFields` + 前端 `isTenantGroupMember` 两道**读取时**的守卫兜底。

**建议（P2）**：写一个 `validateSubs()` 校验函数，在 `UpdateFleetCategory` 入口拒绝非法键（白名单），把守卫从「读时清理」前移到「写时拒绝」。

### 3.5 `billing_tenant_items` 唯一键依赖应用层归一化

- 唯一键 `(billing_tenant_id, item_key)`。
- 「功率因数 / 功率因素」两种写法历史上并存，靠应用层 `normalizeBillingItemKey` 归一 + `OnConflict` 兜底。
- 实测库中现在只剩 1 条「功率因数」✓。

**建议（P2）**：加一条 `CHECK (item_key NOT LIKE '%功率因素%')`，让 DB 层也拦住，避免新代码绕过归一化。

### 3.6 历史废弃键残留

- `subs` 中 `total_fee`（总电费）属于**费用清单默认分组的业主视角列**，是合法字段，**不是**旧「合计应付」——确认无需清理。
- `item_total`（旧合计应付）已在第 18 轮迁移中全部替换 ✓。
